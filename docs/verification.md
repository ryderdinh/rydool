# Verification status

Updated November 1, 2026. These are development results, not release certification.

## Verified

- Environment: macOS 15.3.2 on Apple Silicon, Xcode 16.2/Swift 6.0.3, and one 2x display.
- An earlier `swift test` run covered 20 tests for quotas and rollback, pinning, deduplication and persistence, protection against future schemas, default-on monitoring, pause, markers and exclusions, app selection/removal and preservation of existing settings, avoiding the loss of external copies after screenshots, queue ordering, cancellation of pending data on pause/clear, images and thumbnails, selection/renderer/annotations using synthetic images, and default screenshot key codes. A later run on November 1, 2026 passed 52 tests; after renaming the shortcut test, that test also passed separately.
- The debug build was built universal for arm64/x86_64, signed ad hoc, and its signature verified. The arm64 build was launched; history and simulated region-capture UI tests also ran as x86_64 through Rosetta. Rosetta is not a substitute for testing on a physical Intel Mac.
- `python3 Tests/UI/run-smoke.py`: uses an isolated store, preferences, and pasteboard. It checks the menu, monitoring enabled by default, the global clipboard shortcut, search, pinning, arrow-key/Enter selection, copying, and pinned SQLite data, as well as the explanation and cancellation of the capture permission window when permission is absent.
- `python3 Tests/UI/run-exclusions-smoke.py`: uses a fixture app and isolated preferences to select an app in the macOS dialog, display its name, and remove it; an existing exclusion remains unchanged.
- `python3 Tests/UI/run-capture-smoke.py`: uses synthetic images and an isolated store and pasteboard. It checks automatic copying after region/full-screen capture, capture cancellation, editing, save-dialog cancellation, and PNG export. With history enabled, the original image appears once, copying the edited image creates a separate item, and saving alone adds no item. With history disabled, the image is still copied but is not recorded. The input is not real screen content.
- A debug build signed with the same identity was launched through Launch Services and used to capture the real screen with history disabled, a named pasteboard, and a temporary store. The PNG appeared automatically on the test pasteboard while the general clipboard change count remained unchanged. The test preview was closed and the test pasteboard released.
- Preview behavior was tested with simulated data: region/full-screen capture, opening the editor, canceling back to the preview, copying PNG, and closing the image. Two successive captures retained two independent previews. The UI test used separate shortcuts and did not change the general clipboard.
- Preview auto-hide after five seconds, pausing the countdown while hovering or while the save dialog is open, reopening a hidden image from the menu, and copying through an isolated pasteboard were tested. The release build was also used to capture the real screen, wait for auto-hide, reopen the image from the menu, and close it without copying or saving. Hidden images remain in memory only until the app quits or they are closed.
- After the preview was made smaller, its window size, buttons, and countdown were tested with synthetic images. The release build also opened and closed a small preview from a real screenshot without copying or saving.
- The separate editor window was tested using synthetic images: its window was smaller than the display and showed the image canvas and toolbar; closing the window or pressing Esc returned to the preview. Drawing, undo, Unicode text, save cancellation, and PNG export were tested. Region and full-screen capture pixel dimensions were preserved on export. With the release build, a real screenshot was captured, opened in the separate editor window, and closed without copying or saving the test image.
- A newer release was signed with Apple Development. Two signatures using the same identity had matching designated requirements, the signature was valid, and the release contained no simulated-image hook. After resetting only Rydool's old Screen Recording record and granting permission again, a real full-screen capture showed a preview. Capture also succeeded after reopening Rydool. Both test images were closed without copying or saving. This verified the flow and permission, not per-pixel color accuracy.
- The **release** was opened through Launch Services (`open .../Rydool.app`) after Screen Recording was enabled and the app reopened. Real full-screen and region captures were started on a 2x display, the editor was confirmed to appear, and both captures were canceled. Screen image content was not saved, copied, or read into the test results. The editor appearing does not establish per-pixel accuracy.
- A region of a real black-and-white sample window was captured on a 2x display, saved temporarily as PNG, and checked for 320×320 dimensions and black/white pixel positions; the temporary file was deleted. A blue sample had an unexplained color difference, so color accuracy has not been established.
- The real-capture tests above used a release from before the default shortcuts changed. The later build was built, signed, and reopened; UI shortcut tests used separate combinations to avoid triggering another running screenshot app. Pressing `⌘⇧4` or `⌘⇧3` while another app uses those shortcuts has not been tested.
- One sample after eight seconds idle, with monitoring disabled, on an arm64 debug build: `ps` reported 0.0% CPU and 52,368 KB RSS. This is a single point-in-time sample, not a long-running test or performance commitment.

UI smoke tests require a logged-in desktop and Accessibility permission for the test process. They temporarily control the mouse and keyboard and use a test mode available only in debug builds. They do not read or change the general clipboard. Add `--x86-64` to the scripts to test the Intel build through Rosetta on a supported machine.

## Not yet verified

- Comprehensive color accuracy of real captures, or revoking and regranting permission after the new signed build was successfully authorized.
- External displays or multiple displays with differing positions and scale factors; the current machine has only one display. No macOS 14 system or physical Intel Mac was available for runtime testing.
- Complete VoiceOver coverage, launch at a real login, all shortcut-conflict scenarios, Gatekeeper on a clean machine, and long-running background operation.
- A SQLite process in a temporary directory was terminated during an uncommitted transaction, and previously committed data remained intact. Actual disk exhaustion and forced app termination at every write step have not been tested; this test does not cover them.

Permission diagnosis: when the executable was launched directly from a VS Code process, macOS attributed the TCC request to VS Code instead of Rydool. Opening the `.app` bundle through Finder or `open` lets the system identify `com.rydool.app` separately. An ad hoc signature may require permission to be granted again after rebuilding; a stable development signature preserves the signing identity, but macOS still decides whether permission is granted.
